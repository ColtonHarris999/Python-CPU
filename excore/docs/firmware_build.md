# excore firmware build flow

No external RISC-V toolchain: firmware is assembled by the self-contained
two-pass assembler at `excore/tools/asm_rv32.py` (plain Python 3 — it is
**not** pinned to CPython 3.14 the way `pycore/tools/` is, because RV32I
encodings come from the RISC-V ISA specification, not from probing a
running interpreter; the empirical-verification house rule applies to
CPython bytecode/opcode facts, not to a fixed, publicly specified ISA).

## Building firmware

```sh
python3 excore/tools/asm_rv32.py excore/fw/list_grow.s -o build/excore_fw/list_grow.hex
```

`list_grow.s` handles both `PY_TRAP_LIST_GROW` (append) and
`PY_TRAP_LIST_EXTEND` (grow-to-fit + copy source LIST/TUPLE).

or via the Makefile step used by every excore RTL test target:

```sh
make excore-fw                # assembles $(EXCORE_FW_SRC) -> $(EXCORE_FW_HEX)
make excore-cpu-test           # depends on excore-fw; runs tb_excore
make excore-test               # excore-asm-tests (assembler unit tests) + excore-cpu-test
```

**The assembled hex is never committed.** It is a build artifact
(`build/excore_fw/*.hex`, already covered by `.gitignore`'s `build/`
entry) regenerated by `excore-fw` every time a test target that needs it
runs — the same discipline as `pycore/programs/*.hex` fixtures that are
generated ahead of time by a committed Python generator, except excore's
firmware hex is *never* committed at all, matching "no external toolchain"
being interpreted strictly: nothing binary that could go stale relative to
the assembler or the source `.s` file ships in the repository.

## Adding a new firmware source file

1. Write `excore/fw/<name>.s` using the RV32I subset documented in
   `rv32i_subset.md` and the MMIO registers documented in `mmio_map.md`.
2. Point `EXCORE_FW_SRC` at it (`make excore-fw EXCORE_FW_SRC=excore/fw/<name>.s
   EXCORE_FW_HEX=build/excore_fw/<name>.hex`) or add a dedicated Makefile
   target following the `excore-fw` pattern.
3. Add assembler-level unit tests for any new pseudo-op or directive usage
   under `excore/tests/test_asm_rv32.py` if the firmware exercises
   something the existing golden-encoding tests don't already cover.
4. Add an `excore/tb/` testbench (or extend `tb_excore.sv` with a new
   scenario) driving the mailbox pins with canned trap messages, per the
   `tb_excore.sv` pattern.
