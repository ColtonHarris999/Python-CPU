# Bytecode compile progress

**Status:** measured
**Subject:** bytecode emitted by CPython 3.14.7 when compiling the
vendored PyCPython compiler (`vendor/pycpython/pycpython/`), classified
against PyCore's opcode catalog (`pycore/targets/pycore.json`) and
image acceptance (`pycore/tools/image_from_source.py`).
**Companion:** [`native_compiler_full_plan.md`](native_compiler_full_plan.md)

This is **not** a list of opcodes PyCPython *emits as a compiler*.
It is the instruction mix of **PyCPython's own source** — what the
hart would have to execute to run that compiler without a subsetting
rewrite.

Generated by `pycore/tools/measure_pycpython_opcodes.py`. Do not edit
by hand; regenerate after ISA or vendor updates.

## How this was measured

```text
for each vendor/pycpython/pycpython/**/*.py:
    co = compile(source, path, "exec", dont_inherit=True)  # CPython 3.14.7
    walk co and every nested code object
    count dis.get_instructions(show_caches=False) by opname
    also count raw co_code units (CACHE occupies imem)
```

- Files: **20**
- Code objects (module + nested): **1782**
- Logical instruction units (`dis`, CACHE omitted): **116159**
- Raw `co_code` units (every 2-byte word, including CACHE): **308676**
- Of those, `CACHE` units: **192517**
- Distinct logical opcodes: **92**

`dis` omits `CACHE` even with `show_caches=True`. Image boot still
stores every two-byte unit as one 64-bit imem slot, so the code-RAM
cost of this mix is the raw count, not the logical count.

Classification uses `pycore.json` `opcodes.*.support`:

| Bucket | JSON `support` | Meaning here |
| --- | --- | --- |
| **Fully supported** | `execute` or `strip` | Hardware runs the opcode (type/oparg ceilings in `note` still apply). `EXTENDED_ARG` is included as fetch plumbing. |
| **Partially supported** | `partial`, or `execute` whose *used* opargs include values outside `supported_opargs` | Hardware runs a documented subset. |
| **Not supported** | `trap`, `reject`, or unlisted | Trap, image reject, or no row in the catalog. |

An `execute` opcode is **not** moved to partial just because it lists
`supported_opargs`. That only happens when this mix actually uses a
disallowed oparg (`CALL_INTRINSIC_1` opargs 2/3/5, and one `RERAISE`
oparg 2 in `parser/pegen.py`).

The **Image** column is whether `validate_code_object` would currently
accept the opcode into a `.pycore` image. Prefix rules (`JUMP_*`) make
that column **optimistic** for `JUMP_BACKWARD_NO_INTERRUPT`.

Code RAM is 32768 slots (`pycore.json` `limits.code_ram_slots`).

raw imem units including CACHE are about **9.4×**.
The unmodified compiler cannot be loaded even if every opcode ran.

## What this means for Plan 3

1. **Do not load this mix onto the hart.** 847 trap/reject/unlisted units plus MAKE_FUNCTION/CALL partial
   semantics plus a code-RAM overrun (logical 3.5×, raw 9.4×).
2. **Highest-count unsupported ops to design around in the firmware
   compiler:** `LOAD_COMMON_CONSTANT` (assert), `LOAD_BUILD_CLASS`
   (classes), `IMPORT_NAME` / `IMPORT_FROM` (imports), plus
   `LOAD_LOCALS` / `MAKE_CELL` / `STORE_DEREF` which ride along with
   class bodies and nested defs.
3. **Closures are uncommon but real.** `LOAD_DEREF`, `MAKE_CELL`,
   `COPY_FREE_VARS`, `STORE_DEREF`, and `SET_FUNCTION_ATTRIBUTE` flag 8
   sit on the same nested functions. The firmware compiler should reject
   nested defs that need cells rather than emitting these.
4. **Generators are concentrated in `parser/` and `tokenizer.py`.** A
   PEG-free LL(1) parser does not need `YIELD_VALUE`.
5. **`JUMP_BACKWARD_NO_INTERRUPT` is reject in the ISA.** Fix the image
   builder prefix leak before any generator-loop experiment, or the
   loader will accept a jump the execute loop does not implement.
6. **`CALL_INTRINSIC_1` opargs 2/3/5** (`IMPORT_STAR`,
   `STOPITERATION_ERROR`, `UNARY_POSITIVE`) need either runtime support
   or firmware-compiler rewrites (`+x` → `x`, import-star rejected).
7. **Fully-supported count is necessary but not sufficient.** `LOAD_ATTR`
   still traps on LIST, so `list.append` in the vendor tree would trap
   even though `LOAD_ATTR` itself is `execute`.

Plan 3 therefore does **not** try to execute this opcode mix. The
firmware compiler is a subset rewrite that only emits (and only uses)
allowlisted ops.
